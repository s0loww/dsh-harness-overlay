# Аудит проверок и деплоя сборки Олега

Дата: 2026-11-04. Источник: локальный `dsh-1c-bundle` из релиза `DSH-Desktop-1C-0.1.0-20261103-134539-win-x64`. Это **статический аудит исходников**, а не подтверждение работоспособности установленной платформы 1С. Скрипты, проверки баз, COM, клиент 1С и операции деплоя не запускались; базы и live-установка не менялись. Значения подключений и секретов в документ не включены.

**Вывод:** полезнее перенести устройство планирования, проверки результатов, учёта изменений и владения процессами, а исполняющий слой собрать вокруг наших проектных способов деплоя. `onec_deploy check` у поставщика **загружает изменения в конфигурацию базы**, хотя не вызывает реструктуризацию. Автоматического отката базы у этого центра деплоя не найдено. Установленные средства резервирования состояния DSH не являются резервной копией информационной базы.

Исключённые ранее ассистент, голос, Jira, поддержка поставщика, обновление сборки и Live2D не предлагаются к переносу. Существование проверки этих компонентов в общем readiness также не означает, что она нужна в нашей сборке.

## 2. Как трактовать PASS

| Слой | Что именно означает успех в исходнике | Чего он не доказывает |
|---|---|---|
| Raw Designer runner | `DumpResult=0`; для обычного dump также нужны выходные файлы. Для extensions допускается ноль файлов. [D4] | В этой ветке ненулевой exit сам по себе не отменяет `DumpResult=0`: итоговое условие не требует `exitCode===0`. Явные текстовые diagnostics отдельно не классифицируются. Нельзя использовать её как универсальный строгий checker. |
| PowerShell deploy step | Требуются exit=0 **и** DumpResult=0. Для CheckModules/applicability/CheckConfig дополнительно блокируются явные ошибки **и предупреждения**, после удаления точных «0 ошибок» success-фрагментов. [Q7] | Это не бизнес-тест, не UI-test и не доказательство прав другого пользователя. Политика warnings-as-errors должна быть согласована с проектом, а не скрыта. |
| Runner `done` / receipt.success | В обычном завершении host проверяет exit=0 и наличие разобранного плана; пишет receipt для non-plan запуска. [Q6] | Сам host condition не требует полного множества ожидаемых стадий и события complete. Нужна дополнительная проверка planned stages → observed stages, включая disabled/skipped/no-changes. |
| `deployVerification` | Нет failed среди load/module/applicability/config checks и есть хотя бы одна done module/applicability проверка; отдаёт scope из плана. [Q8] | Не доказывает прохождение **всех** запрошенных проверок и не сверяет hashes файлов. Сама загрузка не считается проверкой. |
| Evidence ledger | Может пометить BSL `partial`, `stale`, `unverified`; изменения после старта Designer делают evidence stale. [E1] | Внешняя запись в файлы и изменение базы вне наблюдаемых инструментов не обнаруживаются; после перезапуска in-memory evidence теряется. |
| Readiness `ok` | Достаточность представленных настроек/доступности. [R1], [R2] | Ни выполненных тест-кейсов, ни актуального исходника в ИБ. Нужны отдельные поля `readiness` и `verification`. |

В поставленном `package.json` test scripts ссылаются на `../test/*.test.mjs`, acceptance/smoke и соседние validators. [U1] **В изученной распаковке этих каталогов/validators нет.** Поэтому количество и результат upstream тестов этой поставки подтвердить нельзя; комментарии «проверено на версии…» считаются заявлением автора, а не нашим измерением. Ничего из test scripts не выполнялось.

## 3. Где plan / dry-run не равен read-only

1. **`onec_deploy check`** — не dry-run: он пишет конфигурацию базы перед проверками. `updateDb=false` выключает только заключительную стадию обновления БД. [Q1], [Q4]
2. **`Invoke-1CEdit -Preview`, alias `-DryRun`** без native DryRun у вызываемого инструмента запускает **настоящий** tool, затем пытается вернуть файловое дерево. Git backend использует checkout/clean; copy backend восстанавливает только watched scope. Поэтому preview требует права на запись, не является DB transaction, не компенсирует внешние эффекты и может оставить частичный результат при сбое отката. Если tool имеет собственный DryRun, wrapper передаёт флаг ему. [V1]
3. **`db-cfe-admin -DryRun`** для delete/set-properties сперва получает текущее состояние расширений. Это реальное подключение/процессы и временные файлы, хотя соответствующее изменение ИБ не выполняется; это не offline planner. `Force` разрешает настоящее изменение/удаление расширения вместе с его данными. [I3]
4. **`db-load-git -DryRun`** имеет отдельный early return до temp directory и загрузки; изученная ветка показывает список файлов без применения. Не следует переносить этот вывод на остальные db-ops scripts: многие вообще не имеют DryRun. [I4]
5. **`onec_designer dump/extensions`** — не запись в базу, но запись в проект; `cleanLocks` дополнительно удаляет lock-файлы базы. [D3]
6. **Полный preflight** может выполнять probes и писать freshness ledger. Passive status должен пользоваться уже собранным snapshot. [P1]
7. **Local extension check** реально исполняет код проверяемого расширения. **QA start/capture/stop** создают процессы/артефакты, а QA действия могут менять ИБ. [X1], [T1]

Отдельно: низкоуровневый `commit=true` в deploy runner выполняет git add/commit выбранного scope после изменения ИБ. Если Git-стадия упадёт, база уже могла успешно измениться; общий failed нельзя выдавать как «деплоя не было». [Q4]

## 4. Ограничения backup / rollback / секретов

- QazDefense runner прямо сообщает, что выполненные стадии при cancel **не откатываются**. Multi-target wrapper имеет честное состояние partial. Нужен отдельный recovery manifest, а не переименование cancel в rollback. [Q6], [O1]
- `ConfigDumpInfo.baseline.xml` — marker сверки, **не резервная копия**. Он обновляется после load, до последующих проверок/UpdateDB; провал этих стадий не возвращает прежнюю конфигурацию. [Q4], [Q5]
- `db-dump-dt` / `db-load-dt` существуют как самостоятельные операции, но наличие restore script не подтверждает восстанавливаемость конкретного backup, совместимость версии и приемлемый RPO/RTO. Нужен drill на отдельном стенде. [K1]
- `restoreState` делает pre-restore backup, проверяет allowlist/hash и пофайловую гонку; записывает файлы последовательно. Это не единая атомарная транзакция всего состояния и не откат информационной базы. [K2]
- COM передаёт payload через stdin. Designer-процессы получают параметры аутентификации через argv, хотя отображаемые команды и сохранённые логи маскируются. Маскирование UI не скрывает argv от локального администратора. При адаптации нужен отдельный threat model; секреты нельзя включать в план, receipt, evidence, CLI примеры или коммит. [D1], [M2], [Q7]

| Связь | Что надо заменить |

## 6. Конкретный предлагаемый план без включения деплоя

**Этап A — единый read-only контракт проверок.** Описать capabilities для локальных XML/UTF-8 и BSL LS, синтаксиса через фасад, платформенных checks, project test runner и QA. Собирать результаты с `checkId`, target/source identity, engine/version, перечнем файлов и SHA-256, planned/actual scope, timestamps, diagnostics/coverage и отдельным verdict. `unknown`, `partial`, `stale`, `skipped`, zero cases и infrastructure failure не преобразуются в PASS. UI использует этот snapshot, не скрытый полный preflight.

**Этап B — неизменяемый deploy plan.** Adapter каждого проекта должен **построить план без исполнения**: какая база/конфигурация/расширение, точный source hash и scope, последовательность, ожидаемые проверки, возможное завершение сеансов, backup provider, recovery route. Зафиксировать выявленные широкие операции, root descriptor и отсутствие baseline. Сверить этот контракт с Эквадором, КА2 и БЛ; БКИ использовать только как файловый/rollout стенд, а не как автоматически пригодную БД для испытаний. Этот документ не подтверждает, что проектные способы уже сопоставлены.

**Этап C — перенос вспомогательной механики.** Реализовать native process ownership, single-flight по target, маскирование, receipts, корректный timeout/cancel, path/reparse guard, агрегацию evidence. Отдельные адаптеры для проектных Designer/ibcmd/существующих runner. Никаких автоматических установок платформы, регистрации COM, публикации базы, изменения MCP или создания test extension при открытии настроек.

**Этап D — проверка adapter на изолированных fixtures.** Без реальной ИБ: Unicode paths, quoting, аргументы, stdout/stderr, код завершения, отсутствующий DumpResult, late result file, warnings, partial scope, injected failures, потеря ownership, XML DTD, malformed encoding, изменение файлов после plan, no-changes и cancel. Должны различаться base/extension, load/check/update и частичный batch. Для PowerShell требуется настоящий contract test парсера событий; один JS mock runner недостаточен.

**Этап E — согласованный проектный стенд.** Сначала проверить backup/restore и идентичность цели; затем последовательно dump, load-config + checks, update-db и acceptance tests. Подтверждение относится к конкретному reviewable плану; действующие пользовательские разрешения повторно не запрашиваются. После загрузки — проверки фактической конфигурации/расширения и smoke проекта; после UI/бизнес-тестов — cleanup только собственных fixtures. Связать hidden desktop с одним владельцем QA клиента и корректным освобождением лицензии. Включение реального deploy — отдельный следующий шаг после сравнения проектных процедур.

**Не переносить сейчас:** default-on UpdateDB/dynamic в общем runner, автоматическую очистку `.cfl`, массовое удаление расширений, прямой COM method fallback, supplier-specific raw MCP wiring, supplier support/update readiness, глобальный Git commit и обещание автоматического DB rollback. Наиболее ценные ближайшие результаты — проверяемый план и честный evidence, а не новая кнопка «успешно».
