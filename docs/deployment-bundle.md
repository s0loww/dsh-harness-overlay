# Единый пакет DSH: API и восстановление

Пакет устанавливает официальный Windows x64 DSH и наши дополнения одной
командой, поднимает локальный Cognee и подключает согласованный комплект MCP.
Инструкция для коллег находится в [deployment-colleague-test.md](deployment-colleague-test.md).
Этот документ предназначен для сопровождения установщика.

## Состав и границы

`Setup.cmd` сначала вызывает поставляемый Python и `bootstrap.py`, затем
поставляемый Node и `payload/engine/src/deployment-bundle/cli.mjs`.
Node, Python, MinGit, официальный установщик DSH, образы и модели Cognee,
установщики Docker Desktop/WSL входят в пакет. Клонировать репозиторий и
собирать проект на компьютере получателя не требуется.
Распаковывать нужно в короткий доступный путь, например `D:\DSH` или
`C:\DSH-Airules`. Если запись в корень C запрещена, выбрать свой доступный
диск. Глубокие пути под Downloads могут превышать ограничения Windows Explorer.
Для передачи используется внешний ZIP с короткими именами: engine находится
в `payload/engine.zip`, а не тысячами глубоко вложенных записей внешнего ZIP.
Bootstrap извлекает его с безусловным Windows `\\?\` prefix, проверкой точного
inventory, SHA/CRC и запретом перезаписи измененных файлов. Имена immutable
артефактов и цепочка исторических квитанций при этом сохраняются.

`deployment-manifest.json` перечисляет каждый поставляемый файл с длиной и
SHA-256. Manifest не включает сам себя: его SHA-256 является идентификатором
пакета в плане и квитанции. Manifest содержит `paths`, `components`, версию
официального DSH и ожидаемый Authenticode thumbprint установщика. SHA-256
защищает от повреждений и рассогласования содержимого; это не цифровая подпись
пакета и не защита от целенаправленной замены всего manifest доверенным
пользователем. Официальный EXE дополнительно проверяется Authenticode.

Пакет приватный: `payload/private` содержит общие учетные данные MCP для
согласованной группы. Папка сборки и ZIP создаются с ACL владельца и SYSTEM.
Архив не шифруется; после передачи или распаковки права доступа зависят от
способа передачи и компьютера получателя. Не публиковать пакет в Git или Releases.
Личные чаты, входы, проекты и история автора не включаются.

MCP-фасад не является зависимостью установщика. Деплой информационных баз
и проектных приложений эта установка не запускает.

## Создание пакета

```powershell
node scripts/build-deployment-package.mjs --output-root "D:\Builds\DSH-test" --extras-root "D:\Staging\extras" --no-archive
```

`output-root` должен отсутствовать. Повторная сборка поверх существующей папки
запрещена. По умолчанию runtime, Cognee и vendor assets берутся из
`var/deployment-assets`. Сборщик копирует точный список трех файлов Cognee,
проверяет pinned SHA образа, моделей, Docker, WSL и официального DSH. Он
сохраняет расположение относительных imports engine и копирует весь vendored
YAML вместе с его CommonJS `package.json` и лицензией.

Экспорты `scripts/build-deployment-package.mjs`:

| API | Назначение |
| --- | --- |
| `buildDeploymentPackage(options)` | Новая папка пакета; архив по умолчанию, `archive:false` оставляет папку для приемки. |
| `collectEngineFiles(sourceRoot)` | Замыкание относительных imports, обязательных scripts, installer и файлов deployment engine. |
| `refreshDeploymentEngine({outputRoot,sourceRoot})` | Для приемочного стенда: обновить engine и инструкцию, пересчитать их строки manifest. Полная повторная проверка перед архивированием обязательна. |
| `prepareDeploymentEnvelope({outputRoot,pythonPath?})` | После приемки полной staging-папки создать engine.zip, bootstrap и launchers; добавить ZIP и исходные engine-файлы в manifest. |
| `finalizePackageInventory(outputRoot)` | Пересчитать inventory всех файлов и полностью проверить пакет. |
| `archiveDeploymentPackage({outputRoot,pythonPath,archivePath})` | ZIP64 поставляемым Python; повторное открытие и проверка CRC всех записей, затем SHA-256 архива. Отказывается заменять существующий архив. |

`refreshDeploymentEngine` применяется только к еще не выпущенной папке
приемки. После передачи коллегам изменения образуют новую версию пакета.
Не добавлять в его папку логи с ключами или пользовательские данные: финальный
inventory включает все находящиеся там файлы.
Папка `--no-archive` служит staging для приемки и до `prepareDeploymentEnvelope`
не является готовым комплектом для передачи через Setup. После envelope выполняются
финальный inventory и outer ZIP. Outer ZIP исключает распакованный `payload/engine/`,
но сохраняет engine.zip; после bootstrap полное содержимое соответствует manifest.
На matching files bootstrap не записывает новые байты; ACL и содержимое проверяются
повторно. При ошибке ACL, CRC, SHA, ссылках, лишних/повторных ZIP entries или чужой
правке bootstrap отказывает и Node не запускается.

## Программный API установщика

```js
import {createDeploymentService} from './src/deployment-bundle/lib/core.mjs'

const service = createDeploymentService({
  bundleRoot: 'D:/Packages/DSH-test',
  stateRoot: 'D:/DSH-state',
  installRoot: 'D:/DSH-app',
  dshHome: 'D:/DSH-home',
  adapters, // штатные host adapters + Cognee/MCP/extras из components.mjs
  onProgress: ({phase}) => console.log(phase),
})
const plan = await service.plan({mode: 'install'})
if (plan.status === 'ready') {
  const result = await service.apply({planId: plan.planId, acceptPlan: true})
}
```

Все четыре пути абсолютные. `stateRoot`, `installRoot` и `dshHome` не должны
вкладываться друг в друга; источник пакета и `stateRoot` тоже разделяются.
Символические ссылки, junction/reparse-переходы и hard links файлов в
управляемых путях отклоняются. Относительные пути manifest не допускают
`..`, Windows device names, ADS и коллизии регистра.

| Метод | Поведение |
| --- | --- |
| `plan({mode})` | `install`, `update` или `repair`; читает и проверяет пакет/состояние, возвращает изменения и конфликты без записи в целевые каталоги. |
| `apply({planId,acceptPlan:true})` | Принимает только план этого экземпляра service; повторно проверяет пакет и сравнивает состояние с планом, затем устанавливает. |
| `status()` | Текущее установленное развертывание и безопасный список `pending`; не проверяет все payload bytes. |
| `rollback({deploymentId?})` | Откат последнего установленного развертывания; произвольный выбор старого ID запрещен. |
| `uninstallOverlay()` | Последовательно откатывает все управляемые версии, максимум 64. Сохраняет базовый DSH и данные памяти. |

Полный набор компонентных adapters формирует `createComponentAdapters()` из
`components.mjs`. Контекст содержит `bundleRoot` приватного cache,
`sourceBundleRoot`, `engineRoot`, `stateRoot`, `installRoot`, `profileRoot`,
`dshHome`, `deploymentId`, `manifest`, `nodePath`, `pythonPath` и `signal`.
Конфигурация компонента возвращает его квитанцию, которую получит его rollback.
При незавершенной операции adapter может приложить `error.componentReceipt`:
plain object будет сохранен для последующего расследования, но неизвестный
результат не превращается в успешный откат.

## Порядок установки и сохранение данных

Установщик получает эксклюзивный `deployment.lock`, проверяет, что DSH
остановлен, копирует package в стабильный `stateRoot/package`, устанавливает
официальный host при отсутствии и создает только отсутствующие файлы профиля.
Проверка процессов использует явный JSON-массив CIM и до трех попыток при
ошибках запуска/разбора или неполном снимке. Для продолжения необходим новый
полностью валидный снимок; неизвестные процессы не отбрасываются. Постоянно
недоступные пути EXE и неверные PID останавливают установку. Пустой stdout
не считается пустым списком процессов; injected query не повторяется.

Далее устанавливаются extras, создается изолированный candidate, выполняются
его цикл apply/rollback, startup smoke и preflight. Только затем применяется
overlay штатным official-live engine, настраиваются машинные пути, Cognee и
MCP, проверяются итоговые управляемые файлы и фиксируется `current.json`.

Существующие credentials/chats/MCP не копируются из профиля автора.
Конфигурация получателя сохраняется с проверкой конфликтов. Ранее подключенный
Cognee повторно используется только после проверки его конфигурации и health.
Измененные получателем machine settings и bootstrap-файлы при удалении
overlay сохраняются и перечисляются как `preservedModified`.

`repair` разрешает восстановить измененные **принадлежащие установщику**
cache-файлы, предварительно сохранив фактические байты. Это не разрешение
перетирать чужие файлы или обойти конфликт package/overlay.

Штатный onboarding DSH добавляет собственные настройки в `cordis.patch.yml`.
Проверка ownership допускает такие посторонние строки, сохраняя строгие хеши
всех управляемых пакетов. Native installer по умолчанию сохраняет прежний
строгий режим rollback; deployment adapter явно включает `preserveUnmanagedCordis`.
Трехстороннее восстановление использует baseline B, установленный документ A
и текущий C: отменяет только изменения установщика и сохраняет посторонние
настройки/форматирование C. Изменение принадлежащего установщику блока,
неоднозначные ID, aliases и shadow-ID collisions отклоняются.

Новые native квитанции сохраняют `after/cordis.patch.yml`, проверяемый по
исходному `operations[].after`. Для старой квитанции допускается лишь точное
воспроизведение pinned fragments/migration с совпадением этого хеша. Перед
rollback сохраняются отдельные observed/restored документы, запечатанный proof
и журнал намерений/перемещений в `rollback-preservation/<id>`. Исходные операции
и их хеши не переписываются. CAS проверяет наблюденный C и прочитанные байты
квитанции; конкурентная правка не перезаписывается. После аварийного выключения
этот native журнал служит ручному восстановлению, а не обещает автоматическое
возобновление прерванного swap.

## Квитанции и линейный журнал cache

В `stateRoot` сохраняются:

- `current.json`: текущая установленная версия и ссылка на квитанцию;
- `cache-state.json`: принадлежащие установщику файлы стабильного package;
- `deployments/<id>/receipt.json`: стадии, компоненты, предыдущая версия,
  bootstrap/machine metadata и результат восстановления;
- `deployments/<id>/cache-journal.jsonl`: журнал копирования cache;
- `components/*`: квитанции и бэкапы отдельных компонентов;
- `package/payload/engine/var/live-promotion-backups/*`: квитанции overlay.

JSON-квитанции имеют `integritySha256`, вычисленный по каноническому JSON.
При обновлении старые артефакты и предыдущие квитанции сохраняются: это
необходимо для отката по цепочке.

Cache journal дописывается, а не перезаписывается целиком для каждого файла.
Для файла записываются два небольших sealed JSONL-события:
`prepare(index,row)` до записи и `commit(index)` после атомарного rename.
Объем журнала O(n), а не O(n²); чтение ограничено 64 MiB. События проверяются
на integrity, порядок индексов и допустимый путь бэкапа. Незавершенная
последняя строка не считается завершенным событием.

Если rename прошел, а commit не записался, восстановление сравнивает реальные
байты с `before`/`after`: `before` уже восстановлен, точный `after` можно
восстановить из бэкапа или удалить, любые другие байты дают конфликт.
Это также делает повтор восстановления идемпотентным и сохраняет чужую правку.

## Сбой и восстановление

При обычном перехваченном сбое установщик компенсирует завершенные компоненты
в обратном порядке, затем восстанавливает cache. Официальный host и данные
памяти остаются. Результат `failed-restored` означает, что все предусмотренные
компенсации завершились. `recovery-required` означает неизвестный исход
компонента, конфликт восстановления либо поврежденный журнал; его нельзя
трактовать как откат.

1. Сохранить путь `receiptPath`, код ошибки и каталог `stateRoot`. Не пересылать
   `payload/private`, auth-файлы или полный каталог памяти в общий чат.
2. Закрыть DSH, включая tray/background-процессы. Проверить `receipt.json` и
   `recoveryFailures`; для частичного компонента проверить его собственную
   квитанцию в `components`.
3. Для установленного overlay использовать `operations.cmd rollback`.
   Незавершенный rollback имеет `rollbackCompleted` и возобновляется с
   незавершенного шага. Не удалять уже выполненные отметки.
4. Для `recovery-required` после незавершенной **установки** автоматического
   общего `recover` сейчас нет. Новый план и apply блокируются кодом
   `DEPLOY_RECOVERY_REQUIRED` до разрешения незавершенного состояния. Сначала
   установить фактический исход компонента по квитанции и данным на диске.
5. Если остался lock после аварийного завершения процесса, сначала убедиться,
   что установщик больше не работает, и сохранить его журнал. Удаление stale
   lock — ручная операция сопровождения, не часть обычной установки.

Полное выключение питания во время apply не покрывается автоматическим
возобновлением всех стадий. Журналы помогают установить исход; отдельный
rollback/recovery API для каждой незавершенной стадии требует дальнейшей работы.
Перед новым планом и apply проверяются все deployment receipts: integrity,
владелец путей и окончательный статус. `preparing`, `recovery-required`,
`rollback-interrupted`, неизвестный статус, отсутствующая либо поврежденная
квитанция блокируют новую установку. Исторические `installed`, `rolled-back`
и `failed-restored` этому не мешают. `status` и diagnostics показывают только
ID, статус, путь квитанции и ограниченные коды ошибок; содержимое компонентов
и auth-файлов в этот список не попадает.

## Производительность и приемочные ограничения

Хеширование выполняется потоково: TAR/EXE не загружаются целиком в RAM.
План и apply повторно читают весь inventory, поэтому пакет с тысячами мелких
файлов на Windows проверяется заметно дольше простого копирования TAR. Текущий
тестовый пакет содержит около 12 тысяч файлов и 3.2 GiB без сжатия.

Нужны место для распакованного пакета, приватного cache, candidate, предыдущих
бэкапов, Docker images и постоянных volumes. Минимальные рекомендации для
приемки: 20 GiB свободного диска, 8 GiB RAM и актуальная Windows 11 x64 с
виртуализацией. Docker/WSL могут потребовать администратора и перезагрузку;
их лицензионные условия не принимаются автоматически.

Manifest ограничен 50 тысячами файлов, 32 GiB на файл и 64 GiB всего;
дополнительно действует ограничение JSON-reader 16 MiB. Эти пределы не заменяют
измерение реального времени/диска на компьютере коллеги. Качество русского
текста и терминов 1С у включенных локальных моделей проверяется отдельно от
технического health и не считается доказанным одним успешным запуском.

Проверки самого механизма: `deployment-bundle-core.test.mjs`,
`deployment-cache-journal.test.mjs`, `deployment-process-query.test.mjs`,
`deployment-package-builder.test.mjs`. Интеграционная приемка полного пакета
проводится в отдельном root с отдельными DSH_HOME и Electron user-data;
реальный деплой проектов не запускается.
