# Cognee в полном установочном пакете DSH

Реализован отдельный компонент `src/deployment-bundle/cognee`, без зависимости от
MCP-фасада и без переноса существующей памяти. Он поставляет официальный Cognee
1.6.7 и локальные модели, создаёт чистый экземпляр на компьютере получателя и
возвращает настройки для штатного экрана памяти DSH.

## Контракт установщика

ESM-модуль `adapter.mjs`, фабрика `createCogneeAdapter()`:

| Метод | Результат и границы |
|---|---|
| `detect()` | Проверяет локальный Docker Linux Engine и современный Compose plugin, сообщает версии/ресурсы. Не запускает и не перезапускает Docker Desktop/WSL. |
| `exportOfflineAssets({destination,sourceContainer})` | Только сборочная операция: официальный образ через `image save`, фиксированный список файлов публичных моделей через чтение кэша. Не экспортирует контейнер или пользовательский том. |
| `install({stateRoot,assetsRoot,port,ownerSid,...})` | Требует новую пустую папку и свободный loopback-порт. Проверяет хэши, загружает локальный образ, создаёт собственный пустой том, добавляет только модели, создаёт новые серверные секреты и обычного пользователя DSH с новым API-ключом. |
| `start({stateRoot})` | Запускает только экземпляр из собственного receipt. При повторном создании проверяет неизменность compose и закреплённый образ. |
| `health({stateRoot})` | Проверяет принадлежность экземпляра, готовность и версию; секреты не возвращает. |
| `stop({stateRoot})` | Останавливает только собственные контейнеры, сохраняет данные. |
| `uninstall({stateRoot,purgeData:false})` | Удаляет только контейнеры/сети с совпавшим ownership label. Том по умолчанию остаётся. Его удаление требует явного `purgeData:true`; общий образ не удаляется. |

`install` возвращает `memoryHome`, `configPath`, `authPath`,
`processingBindingPath`, `processingPath`, `endpoint`, `container`, `volume`,
`stateRoot`. Внешний установщик размещает эти четыре файла в фактическом профиле
DSH по своему receipt, сохраняя машинный `composeDir` из binding. В ответе нет
пароля, ключа или токена.

На Windows внешний установщик передаёт SID текущего пользователя и защищает
машинную папку ACL текущего пользователя и SYSTEM перед provisioning. Файловый
`mode:0600` в Node достаточен для POSIX, но не заменяет Windows ACL. SID также
нужен уже существующему native механизму применения профилей обработки Cognee.

Привязка совместима с `validateProcessingBinding`, конфигурация — с
`validateConfig`, профиль — с `validateProcessing` текущего runtime. Начальное
состояние: Cognee включён, обработка разрешена, fastembed 384 dimensions и GLiNER.
Приоритеты/approval памяти принадлежат существующему DSH runtime; этот адаптер
не меняет проектные правила и не включает платные провайдеры.

| `cognee-models.tar` | 850 636 800 байт | `040152d7c8baa01fd96f603d720c9a01d4300c0f8a895288811a61a580b8a9b3` |
| `assets.json` | Небольшой manifest | Хэшируется внешним manifest пакета. |

Общий размер двух архивов — 1 772 745 216 байт. Сборочные файлы расположены в
игнорируемом `var/deployment-assets/cognee`. Соседние диагностические архивы и
`var/deployment-cognee-smoke` не входят в allowlist и не должны упаковываться.

Образ закреплён digest `sha256:84584eade25cd9526ef4fe8dd550be69fb974fb1083bde9e498da451fad0dfc6`,
upstream commit `8853378eae5366addb064e758e560a456146ae1a`. После `docker load`
используется собственный локальный tag и `pull_policy: never`; проверяется
точный image ID. Существующий tag с другим образом не подменяется.

Модели и ревизии:

- `fastino/gliner2.5-base-v1`: `07d99c0ba5d15cb3b24e0a236fa99bdd4ef87a5c`;
- tokenizer `BAAI/bge-small-en-v1.5`: `5c38ec7c405ec4b44b94cc5a9bb96e735b38267a`;
- `Qdrant/bge-small-en-v1.5-onnx-Q`: `aa8f8b060edb00e03bfdd08813a2949946c8ba55`.

Экспортируются только 11 заранее перечисленных файлов моделей/tokenizer и
три генерируемых `refs/main`. Ссылки HF-кэша превращаются в обычные файлы только
после проверки нахождения исходника внутри model root. При импорте архив не
распаковывается через `extractall`: каждый путь, тип, размер и хэш проверяются.
`.env`, auth-файлы, базы, датасеты, заметки, source-пути, xet logs и cache locks
в архив не включаются. Зафиксированный список не захватит случайную заметку,
добавленную в каталог snapshot.

Cognee/GLiNER — Apache-2.0, BGE/ONNX model cards указывают MIT. Тексты лицензий,
модельные карточки и источники сохранены в `notices/` и поставляются вместе с
компонентом. Официальный образ сохраняет собственные лицензии зависимостей.

## Сеть и необязательные провайдеры

Обычная установка использует Docker bridge и публикует API только на
`127.0.0.1`. Это совместимо со штатными профилями OpenRouter, Ollama и LM Studio,
которые пользователь может отдельно выбрать и настроить в DSH. При установке
нет LLM/API-ключей; загрузка HF-моделей запрещена offline-флагами, feedback
отключён. Локальные модели уже находятся в томе.

Для испытания без внешнего доступа есть `offline:true`: сам Cognee состоит
исключительно во внутренней Docker-сети. Docker Desktop 29 не публикует порты
такой сети, поэтому отдельный контейнер с небольшим stdlib Python relay
публикует loopback API и пересылает соединения только на `cognee:8000`. Он не
читает файлы, не импортирует модели, не разбирает HTTP/ключи и не выбирает
произвольный адрес. У сервера Cognee внешнего маршрута нет. Переход к внешним
модельным сервисам для такого экземпляра требует осознанного изменения сетевого
режима компонента; одна замена имени модели сеть не открывает.

## Выполненные проверки

`node --test tests/deployment-cognee*.test.mjs`: **11 PASS**. Проверены изменённые
артефакты, чужие Docker-ресурсы, свежие секреты, UI-совместимые файлы, отсутствие
автоматического удаления данных и отсутствующий prerequisite.

Настоящий чистый экземпляр `offline-test-03`, порт 18180, новый том, новый
пользователь и ключ: **12 PASS**. Проверены:

- готовность API через loopback relay и отсутствие внешнего маршрута у Cognee;
- HTTP 401 без ключа и отсутствие импортированных датасетов;
- загрузка единственного синтетического текста;
- фактическая обработка GLiNER + локальные embeddings без сети;
- CHUNKS-поиск с исходным текстом и идентификатором выбранного датасета;
- граф: 15 узлов / 21 связь;
- остановка/запуск с сохранением ключа, текста и поиска.

Отчёт: `var/deployment-cognee-smoke/offline-smoke-report.json`. После испытания
его собственные backend и relay остановлены для освобождения памяти. Текущий
Cognee на 18080 не останавливался и не перенастраивался; пользовательские
датасеты не читались и не копировались. Никаких платных модельных вызовов нет.

Две ошибки упаковки были пойманы до PASS и исправлены: лишний перевод строки
в HF `refs/main` мешал offline cache lookup; публикация порта internal-only сети
не работала в текущем Docker Desktop. Финальный хэш model archive выше относится
к исправленному варианту.

Для испытания использовался лимит 3 GiB / 2 CPU; стандартный лимит компонента —
5 GiB / 2 CPU, relay ограничен 64 MiB. В машине Docker было около 6 GiB доступной
памяти перед запуском; другие приложения и сервисы не завершались. Прикладное
качество английской embedding-модели на русских документах/1С этим smoke не
подтверждается; это отдельный выбор профиля в DSH.


## Review интеграции с общим установщиком

Проверены `components.mjs` и `cli.mjs` с навыком `engineering:code-review`.
Закрытые замечания:

- существующее подключение проходит strict loopback-валидацию и проверку ключа
  через identity endpoint; redirect запрещён, датасеты при reuse не читаются;
- частичная чужая конфигурация сохраняется без запуска нового сервера;
- каждый планируемый профильный файл журналируется до записи с точным хэшем;
  при сбое останавливается собственный backend и удаляются только совпавшие
  новые файлы, пользовательские данные остаются;
- неопределённый stop сохраняет ключи и interrupted receipt для recovery;
  ссылка на компонент передаётся внешнему deployment receipt;
- rollback ограничен ожидаемым state root, deployment receipt и четырьмя
  именами файлов памяти: пересчитанный seal сам по себе не разрешает удалять
  посторонний путь;
- CLI защищает state root ACL до установки компонентов, а профильный секрет
  записывается через предварительно защищённый временный файл;
- repair/update reuse сохраняет исходное владение в предыдущей цепочке receipt.

Проверка image ID учитывает два представления тех же закреплённых байтов:
manifest digest в Docker containerd store и config digest
`sha256:03a4c4e763255887295280b2ddaef862c92931f7088f4f792a017c92665ccd36`
из sealed image archive для classic Docker. Неизвестный ID отвергается.
Реальный legacy image store отдельно не запускался; его форма ID проверена
fixture-тестом. Хэши payload от этой совместимости не изменяются.

Человеческий протокол приёмки: `deployment-colleague-test.md`. Полная установка
пакета на чистой Windows остаётся отдельной проверкой внешнего установщика;
локальная offline проверка компонента не выдаётся за такую проверку.
