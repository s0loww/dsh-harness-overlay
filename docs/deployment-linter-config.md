# Локальный линтер в едином пакете

Setup настраивает `DSH_HOME/bsl-linter/settings.json` и `DSH_HOME/bsl-editor/plugin-config.json`. Это настройки данной установки; проектные файлы, MCP и реестр Windows не меняются. Java и BSL LS запускаются из `runtime/java` и `runtime/bsl` пакета. Предварительная установка Java не нужна.

Для новой установки включается LSP редактора, порт 8025, расширения `.bsl`/`.os`, UTF-8, память Java 128–1024 MiB. WebSocket слушает только `127.0.0.1`. Процесс запускается по требованию при открытии редактора. Занятый чужим процессом порт возвращает явную ошибку, редактор не подключается к чужому серверу.

При одновременной работе редактора и агентского LSP создаются отдельные процессы
Java с этим лимитом каждый. Для DSH вместе с локальным Cognee и линтером
рекомендуется 16 GiB RAM; на компьютере с 8 GiB стоит ограничить параллельные
проверки и число одновременно открытых редакторов.

Существующие корректные настройки внешнего сервера, пользовательский порт и выключенный LSP сохраняются. При первом обычном Setup могут быть перенесены старые настройки редактора из LocalAppData в отдельный DSH_HOME; исходный файл не меняется. Изолированные приёмочные установки пропускают этот импорт.

`configureLinter(context)` возвращает receipt с точными резервными копиями изменённых файлов. `rollbackLinter({...context, componentReceipt})` восстанавливает только эти файлы. При последующих пользовательских изменениях откат прекращается с конфликтом, сохраняя новые данные. Ссылки, hardlink и выходы за разрешённые пути отвергаются.

`getLinterEnvironment(context)` возвращает только переменные дочернего DSH: `ONEC_BSL_LS_COMMAND`, JSON `ONEC_BSL_LS_ARGS` и маркер пакетного процесса; `JAVA_HOME` добавляется только при отсутствии своего. Явные переменные сервера пользователя приоритетнее. Глобальные PATH/JAVA_HOME не меняются. Пакетные процессы Java очищают унаследованные JAVA_TOOL_OPTIONS/_JAVA_OPTIONS/JDK_JAVA_OPTIONS только в своём окружении, чтобы внешние настройки и секреты не попадали в журнал Java. Пользовательский сервер сохраняет собственное окружение.

BSL LS 1.0.7 использует `lsp` для stdio и `websocket --server.port=8025 -c <config> --app.websocket.lsp-path=/lsp` для редактора. JVM-параметры стоят перед `-jar`. Редактор выбирает `.bsl-language-server.json` выбранного проекта, затем машинный fallback с `language: ru` и `sendErrors: never`. Агентский LSP запускается с рабочим каталогом проекта и сохраняет штатный поиск проектной конфигурации. Проектные runners со своей закреплённой версией линтера остаются независимыми.

Проверка: `node --test tests/deployment-linter-config.test.mjs tests/official-onec-mechanics.test.mjs tests/onec-lsp-compat.test.mjs`. Fixtures проверяют установку/откат, приоритет настроек, конфликт отката, изоляцию candidate, реальный шаблон редактора и аргументы Java без запуска реального деплоя.

Дополнительно выполнены живые проверки: штатный `dsh-lsp-actions` через SDK
rc022 вернул диагностики и символы BSL; точный `startServer` из policy
`0.17.3-linter1` запустил реальный сервер редактора, WebSocket вернул диагностики
и символы. Проектный русский конфиг победил английский машинный fallback.
Слушатель привязан только к localhost; процессы и порты после проб закрыты.
Модели, MCP и деплой 1С в этих проверках не использовались.
