# Дальнейшие интеграции

## Трекеры проекта: YouTrack и Битрикс

Пользователь предложил позже встроить взаимодействие с Битриксом через API и спросил о YouTrack. Сейчас подключения и внешние операции не выполняются.

Предлагаемый общий интерфейс: проектная привязка трекера; чтение задачи/комментариев/вложений; связь с OpenSpec, планом и доказательствами; явная команда публикации отчёта/комментария/смены статуса. Настройки проекта отдельно от машинных секретов; MCP-фасад не обязателен.

- YouTrack: REST API, permanent token с правами пользователя; проекты, задачи, поля, комментарии и вложения. https://www.jetbrains.com/help/youtrack/devportal/youtrack-rest-api.html
- Битрикс24: входящий вебхук для личного подключения, OAuth для распространяемого приложения. https://apidocs.bitrix24.com/settings/how-to-call-rest-api/authorization.html
- Перед реализацией уточнить продукт: Битрикс24 или сайт/CMS «1С-Битрикс», облако/коробка, конкретные необходимые операции.

Внешние записи, сообщения и изменения статусов не становятся автоматически разрешёнными от самого подключения трекера. Текущие данные и учётные записи не импортируются из чужой сборки.

## Обновление нашей сборки из Git

Запрошено пользователем после выпуска компаньонов. Это новый механизм обновления нашей сборки; ранее исключённый обновлятор Олега не возвращается.

Источник по умолчанию: `https://github.com/s0loww/dsh-harness-overlay.git`. В интерфейсе «Обновление сборки»: текущая и доступная версии, ветка/канал или тег, точный commit, совместимость с установленным Desktop, список изменений, проверка, установка и откат.

Порядок реализации:

1. Описание release manifest: версии UI/policy/airules и официального Desktop, commit, хэши, необходимые локальные зависимости. Git содержит исходники, но не полный установочный комплект; подготовить проверенные release-артефакты либо явный локальный build со всеми закреплёнными входами. Простой `git pull` не считается установкой.
2. Fetch в отдельный управляемый checkout/cache. Доступ к приватному репозиторию через существующую Git-авторизацию машины. Не выполнять произвольные post-install hooks из полученного дерева.
3. Собрать/скачать кандидат, проверить manifest, совместимость, хэши и целостность, показать изменение до применения. Обновление официальной оболочки DSH учитывать отдельным совместимым шагом, а не заменой подписанного app.asar из Git.
4. Использовать существующий `installer/official-live`: preflight → backup/receipt → применение → перезапуск в подходящий момент → startup/integrity → доступный rollback. Сохранять пользовательские чаты, аккаунты, MCP и настройки.
5. Негативные сценарии: недоступный Git, отсутствие доступа, несовместимый host, неполный artifact, изменившийся live-профиль, прерванная установка, ошибка запуска и восстановление. Проверка обновлений сама по себе ничего не устанавливает.

Результат этапа: пользователь обновляет нашу сборку из DSH и видит установленную ревизию и путь отката. Правила могут обновляться отдельно от UI/пакетов.

## Раскатка airules в проект из DSH

Встроить адрес canonical-репозитория `https://github.com/s0loww/airules.git` как источник по умолчанию. Пользовательский fork/ветка/тег настраиваются отдельно. Локальный путь — машинная настройка: на текущем компьютере использовать `D:\AI_Projects\project_rules`; у получателя сборки предложить управляемый checkout/cache или существующий каталог. Не требовать наличия диска D: на чужом компьютере.

Страница «Правила проекта» использует общий выбранный проект DSH, без выбора сеанса. Поток: выбрать источник/ревизию и профиль → заполнить общий проектный слой/параметры → построить кандидат → просмотреть diff/конфликты → применить → проверить → при необходимости откатить.

Основа уже существует в canonical `targets/dsh/deepseek/render.py`: `stage`, `verify`, `apply`, `rollback`. Обвязать этот механизм штатным процессным исполнителем и правами DSH, сохраняя manifest, CAS/проверку изменений и резервные копии. Проверить реальный CLI-контракт перед интеграцией. Существующий путь не обязывает делать fetch/pull в пользовательском рабочем дереве с незакоммиченными правками; чистый закреплённый snapshot готовить отдельно.

В интерфейсе предусмотреть:

- «Установить / обновить правила», список управляемых файлов, исходную и целевую ревизию, статус актуальности.
- Общую конфигурацию, пригодную для передачи сборки другим людям, и отдельный локальный/проектный слой.
- Выбор целевого слоя DSH; возможность отдельно выбрать Codex/Claude при последующем расширении с использованием их canonical renderers. Выбор OpenAI-модели внутри DSH сам по себе не делает Codex target обязательным.
- Сохранение пользовательских правил и навыков: не заменять их вслепую при конфликтах. Проектный слой остаётся приоритетнее встроенного rulepack.
- MCP не раскатывать по умолчанию: не переносить токены, чужие endpoints, подключения к базам и персональные пути. Настройка MCP — отдельный явный выбор; наличие фасада не требуется.
- Встроенный rulepack как доступный источник при отсутствии Git/сети; явно показывать его версию. Не представлять старый offline snapshot как последнюю версию репозитория.
- Предпросмотр доступен без запуска модели; запись идёт через штатные права DSH. Кнопка не запускает деплой 1С, проектные тесты или внешние интеграции.

Приёмка: новый пустой проект, обновление управляемых правил, конфликт пользовательской правки, dirty source, offline, Unicode/BOM, смена выбранного проекта, read-only, отзыв прав во время операции, откат и переносимая установка на машине без локального canonical checkout. Отдельно проверить, когда новые инструкции вступают в силу в уже открытом чате; не обещать автоматическую перезагрузку без подтверждённого native API.

Рекомендуемая последовательность: единый источник/кэш и закреплённые ревизии → раскатка airules в проект → обновление пакетов сборки. Трекеры YouTrack/Битрикс остаются отдельной последующей интеграцией.
