# Память Олеговской сборки: Cognee, граф 1С и наша Memora

Проверено локальное дерево донорской сборки `dsh-1c-bundle` и исходники `D:\AI_Projects\memoria`. Это чтение исходников, а не проверка работающих сервисов. MCP-вызовов, индексации, входов, записей в память и переноса Cognee не выполнялось. Адреса подключений, секреты и содержимое пользовательских заметок не исследовались.

## Что у Олега действительно реализовано

Cognee у него подключён достаточно глубоко: есть не только правило «запомни через MCP», но и экран управления, просмотр датасетов/документов/графа, загрузка файлов, запуск обработки и программный слой памяти. **Сам движок Cognee в изученной сборке не поставляется:** installer prompt предлагает отдельно развернуть официальный сервис. Из локального JS нельзя подтвердить его фактическую версию, выбранную БД, алгоритм извлечения сущностей, модель, embeddings или уже накопленные данные.

| Участок | Подтверждение исходниками | Практический смысл |
|---|---|---|
| Выбор хранилища | `lib/project-memory-options.js`, `lib/autonomy-core.js` | Поддерживаются Cognee, OpenViking и локальный файл; проектные настройки выбирают соединение. Правила отдельно описывают templates MCP как следующего получателя записей. |
| Разделение проектов | `projectMemoryOptions()` | По умолчанию имя датасета строится из SHA-256 нормализованного абсолютного пути проекта; разрешено явно заданное имя. На Windows путь приводится к нижнему регистру. Это договорённость клиента, а не доказательство серверной ACL-изоляции. Перемещение проекта изменит автоматически рассчитанное имя. |
| Запись факта | `autonomy-core.js: remember()` | Сначала добавляет локальную запись в приватный проектный `memory.md`, затем обращается к выбранному внешнему backend. Cognee MCP: `remember` с проектным dataset; HTTP: загрузка текста, затем асинхронный запрос `cognify`. Ошибка даёт явный локальный fallback. |
| Состояние обработки | тот же `remember()` и `uploadCogneeFile()` | Хранятся receipt/task ID и признак pending. Принятая загрузка не выдаётся за завершённое построение индекса; повторная загрузка при неизвестном исходе запрещается сообщением интерфейса. |
| Поиск агента | `autonomy-core.js: recall()` | Cognee CHUNKS, top-k 8, с проектным dataset. При недоступности ищет текстовое совпадение в локальном файле и сообщает fallback. Это извлечение записей, без запроса сгенерировать ответ по графу. |
| Поиск из панели памяти | `memory-workspace.js: searchMemory()` | Ищет **по всем читаемым датасетам**, а не только по датасету текущего агента. Через MCP сначала получает список, затем явно передаёт имена; неоднозначные/дублирующиеся имена отклоняются. HTTP-ветка делает общий CHUNKS-поиск. Это сознательно более широкий режим просмотра документов. |
| Просмотр/создание наборов | `DATASET_METHODS`, `datasetCall()` | Поддерживает список и создание датасетов, список документов; возможности проверяются по живым MCP descriptors либо OpenAPI внешнего сервера. |
| Загрузка документа | `uploadCogneeFile()` | Явное подтверждение, выбранный существующий dataset, до 8 МиБ. Через MCP использует `cognify_file`; через HTTP сначала add, затем фоновый cognify. Вся обработка содержимого делегирована серверу. |
| Просмотр исходника | `dataContent()` | Проверяет принадлежность документа выбранному датасету, возвращает ограниченный текстовый preview. Это не отображение произвольного серверного HTML. |
| Граф памяти | `graphPayload()` и действие graph | Запрашивает визуализацию внешнего Cognee для выбранного dataset, ограничивает preview 80 узлами/600 рёбрами. Проверяет согласованность dataset между MCP и HTTP. Глобальные служебные search-event metadata отбрасываются. |
| Настройки Cognee | `settingsContract()`, `savePayload()` | По OpenAPI обнаруживает поддерживаемые параметры LLM/vector backend. Форма не извлекает существующие ключи. Перечитывает настройки после сохранения; отдельно предупреждает, что сохранность настроек после рестарта сервера не подтверждена. |
| Обновление/удаление | `autonomy-core.js: forget()` и список разрешённых UI actions | Локальный forget удаляет тему **только из локального файла**. Точечного удаления/обновления внешней Cognee-заметки в этом программном API и панели не обнаружено. Правила требуют точной поддерживаемой операции; `forget(dataset=...)` в MCP потенциально удаляет весь датасет и не считается удалением одной заметки. |

Имена HTTP-путей выше намеренно не приведены как готовые команды: фактический сервер и его схемы в этой проверке не опрашивались. Код содержит несколько поколений HTTP payload names: autonomy использует snake_case, новый workspace обнаруживает camelCase через схемы. Это совместимость, которую при возможном отдельном переносе нужно проверять на конкретной версии Cognee; наличие JS-коннектора само её не доказывает.

## Память и оркестрация у Олега

Каноническая политика у донора находится в `skills/onec-rules-library/references/rules-1c/project-memory.md`, технические примеры — в `skills/mcp-1c-tools/docs/memory-providers.md`.

- Два уровня: корневой проектный `memory.md` для критических стабильных ограничений и внешняя память для проверенных фактов, решений, исправлений пользователя и полезных процедур. Текущие инструкции и подтверждённый исходник имеют приоритет над памятью.
- Приоритет **записи** по правилам: Cognee → OpenViking → templates MCP. Одна подтверждённая запись, без размножения одинаковой заметки по всем backend. Это политика промптов; программный auto-selector в `autonomy-core.js` сначала предпочитает OpenViking, если он сконфигурирован. Поэтому говорить об одном и том же неизменном приоритете во всех слоях неверно.
- Полный цикл/spec ищет во всех разрешённых провайдерах; быстрый фикс — в первом подходящем. Список настроенных серверов не считается доказательством доступности инструмента.
- `required/off/auto`, неполное покрытие, pending и неоднозначный исход записи описаны отдельно. При timeout нельзя слепо записывать то же во второй backend.
- Полезная процедура живёт в соответствующем skill, память хранит короткий указатель/источник/исход применения. Пользовательские `/learn`, `/lesson`, `/retro` и skill-maintainer относятся к сбору подтверждённых уроков, а не к свободному саморедактированию правил.
- Автоматический hook перед модельным шагом в `autonomy.js` подмешивает до пяти локально подходящих строк `lessons.md` по новому пользовательскому сообщению. Этот конкретный hook не обращается к Cognee/LLM и не доказывает автоматическое чтение всей внешней памяти на каждом шаге.
- Compaction не пишет «выведенные из сводки» факты. `memory_distill` возвращает неподтверждённого кандидата для явного `/learn`, а не сохраняет его автоматически.

## Три разных графа

| Граф | Что являются узлами/рёбрами | Откуда берётся |
|---|---|---|
| Граф объектов/кода 1С | Объекты метаданных, модули, вызовы, ссылки/зависимости; точный состав определяет MCP | У донора `lib/onec-graph-render.mjs` принимает nodes/edges от `1c-graph-metadata-mcp` (`affected_subgraph`, `trace_impact`). В нашей панели `onec-panels/workbench.js` показывается ограниченный фактический ответ MCP выбранного сеанса. UI сам не строит индекс кода. |
| Cognee knowledge graph | Сущности/связи обработанного содержимого, возвращённые внешним Cognee | Донор запрашивает серверную визуализацию dataset. Как именно сервер выделил сущности и отношения, в комплекте не реализовано и не проверено. |
| Memora memory graph | Записи памяти и типизированные связи между ними: supersedes, contradicts, implements, extends, references, related_to | Исходники нашей Memora, включая явный `memory_link`, similarity-связи и результаты absorb. Это не автоматически восстановленный граф вызовов 1С. |

Можно связать подтверждённую заметку с объектом 1С через устойчивый идентификатор и источник, но эти три графа не становятся одной базой автоматически. Визуализация связей не доказывает полноту исходного индекса или истинность семантического вывода.

## Что подтверждено о нашей memoria

`D:\AI_Projects\memoria\PROJECT.md` называет проект собственной сборкой Memora. README описывает возможности, а реализация подтверждается `memora/schema.py`, `memora/storage.py`, `memora/server.py` и `memora/graph/`. Документы сборки исторические и местами по-разному описывают ветки; это не аудит развёрнутого контейнера и не утверждение о совпадении его текущей версии с checkout.

| Возможность | Memora в локальном исходнике | Cognee в локальном доноре |
|---|---|---|
| Хранение | Реально присутствуют SQLite schema: memories, FTS5, embeddings, crossrefs, events/actions; backend abstractions | Только коннекторы и инструкция отдельно развернуть сервис. Тип и состояние фактических БД не установлены. |
| Поиск | semantic/hybrid, tags_any/tags_all, metadata/date filters; ID источников | Агентский и UI CHUNKS-поиск делегирован Cognee. Внутреннее ранжирование не видно. |
| Контекст задачи | `memory_digest`: детерминированная агрегация активных hits, TODO/issues, lineage и ограниченных related hops; source IDs | Набор возвращённых chunks/документы и отдельный графовый preview. Эквивалент digest в изученном donor wrapper не найден. |
| Эволюция знания | `memory_absorb`: поиск похожего, LLM-классификация duplicate/update/contradict/related/new, consolidation; dry_run | wrapper передаёт remember/cognify серверу; логика dedup/supersession сервера в комплекте не видна. |
| Точечные изменения | `memory_get/update/delete`, typed `memory_link`; документные guards и lineage | Внешние точечные update/delete не реализованы в описанной панели; семантику MCP нужно отдельно исследовать по серверу. |
| Проектные границы | Теги/metadata filters и клиентская дисциплина; в рассмотренной базовой таблице нет обязательной project/tenant колонки | Автоматический project dataset у клиентского агента; панель документов намеренно имеет all-readable-datasets поиск. Dataset name не равно security boundary. |
| Графический интерфейс | Своя локальная graph UI/API и дополнительные cloud варианты описаны/реализованы | Cognee UI встроена как панель внешнего сервиса в DSH. |

Вывод для дальнейшего объяснения пользователю: переход на Memora не означает отказ от графовой памяти — она уже имеет свой граф, управляемые версии фактов и retrieval с источниками. У Олега ценно удобство встроенного **рабочего места памяти**: наборы, документы, preview, статусы обработки и граф. Это можно обсуждать как отдельный универсальный UI поверх доступных memory-capabilities, не подменяя нашу память Cognee и не копируя его приоритеты провайдеров в общие правила.

Переносить Cognee, менять маршрутизацию памяти или мигрировать записи эта проверка не предлагает и не выполняет. Для честного сравнения качества/скорости/стоимости понадобятся отдельные одинаковые задачи на тестовых хранилищах и подтверждённые версии обоих сервисов.
