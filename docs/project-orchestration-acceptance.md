# Приёмка DSH на копии реального проекта

Стенд использует один явно выбранный BSL-модуль основного проекта. Оригинальный
проект остаётся только источником: не копируются MCP, `.env`, настройки базы,
проектные runners или живые подключения. Полный сценарий БКИ не используется.

`scripts/probe-project-orchestration.mjs` принимает только явные параметры:

```text
node scripts/probe-project-orchestration.mjs --candidate-root <isolated-candidate> --ui-artifact <ui-artifact> --policy-artifact <policy-artifact> --project-root <read-only-project> --source-relative <relative-module.bsl> --bsl-ls <installed-bsl-language-server.exe>
```

Механическая проверка использует существующие native DSH tools и executor:

1. Побайтовая ограниченная копия выбранного UTF-8 BSL; хеш исходника до и после.
2. `1c-airules`, native read, загрузка persona и pipeline из установленного пакета.
   Native inbox действительно получает локальный AGENTS; проектный handoff
   перекрывает bundled skill. Одноимённый файл `rules/subagent-pipeline.md`
   не заменяет текст, возвращаемый `airules_rule`: это отдельные механизмы.
3. Отказ в edit в read-only и проверка неизменности копии.
4. Анализ копии настоящим локальным BSL Language Server через штатный
   `airules-dsh-workflows` native process adapter, workspace-write и sandbox.
5. Минимальная правка двух маркеров комментария через native edit. Меняется
   только копия: функции, URL и авторство сохраняются.
6. Повторный JSON-анализ: целевые `SpaceAtStartComment` исчезают, остальные
   диагностики сохраняются и честно показываются в отчёте.
7. Native write создаёт handoff, оригинал повторно проверяется по SHA-256.

Выбранный для локальной приёмки пример — небольшой общий модуль из контура
БЛ, имеющий две реальные диагностики отступа после `//`. Это косметическая
правка, не проверка бизнес-поведения проекта. Полные снимки исходника, JSON
линера и результаты остаются только в ignored `var/project-acceptance/`.

## Граница доказательства

Такой запрограммированный сценарий доказывает интеграцию инструментов,
штатных прав, реального процесса линтера и артефактов. Он не доказывает качество
анализа, планирования и делегирования моделью. `airules_delegate` проверяется
на наличие в native registry; настоящий запуск субагента требует настроенной
модели и отдельного живого шага. Probe блокирует любые model requests и все
неразрешённые tool dispatch, включая MCP, deploy и внешние сообщения.

Поэтому итог — `mechanicalExecution: PASS`, но общий `status: PARTIAL`,
`modelOrchestration: NOT_RUN`, `projectVerification: NOT_CERTIFIED`.
Непроходящий sandbox/линтер не заменяется автоматическим повышением прав.

BSL LS 1.0.7 на выбранном UTF-8-BOM исходнике может выдавать lexer notice у
BOM и предупреждения совместимости Java. Ограниченный stderr observer сохраняет
только boolean/category (`bsl-lexer-warning`, `jvm-compatibility-warning`),
не сырой лог. BOM и байты оригинала не исправляются ради зелёного результата.
Успешный exit процесса и уменьшение диагностик не считаются компиляцией 1С
или подтверждением отсутствия синтаксических и бизнес-ошибок.

Следующий живой шаг — запуск согласованной задачи моделью на этой же копии,
с реальным `airules_delegate` и проверкой результата/модели/effort. Рабочие
файлы и базы по-прежнему не являются целью приёмочного изменения. Реальный
деплой, COM, live-IB и внешние отправки остаются отдельными операциями.
