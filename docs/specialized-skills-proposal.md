# Специализированные навыки 1С: предложение адаптации

Дата: 2026-11-07. Это read-only аудит и предложение контрактов. Канонические
навыки ещё не изменены; имена реальных runtime API согласует владелец backend.
Рабочие ИБ, хранилища, MCP, установщики и account-действия не запускались.

## Каноническое размещение

Четыре навыка относятся к технологическому стеку, не к generic core:

- `overlays/1c/skills/1c-repository-manage/SKILL.md`;
- `overlays/1c/skills/1c-ai-merge/SKILL.md`;
- `overlays/1c/skills/v8unpack-cf/SKILL.md`;
- `overlays/1c/skills/1c-element/SKILL.md`.

Переносимые методы и условно читаемые references живут в canonical airules.
DSH предоставляет фактически зарегистрированные capabilities и адаптеры
проектных runners. Навык не создаёт инструмент, доступ или подключение своим
названием. MCP-фасад остаётся необязательным.

Donor — поставляемые файлы `dsh-1c-bundle/skills` из версии сборки пользователя.
Метод нужно написать под наши правила, а не копировать команды, целевой target
или данные окружения. Donor `run: subagent`, `subagent: 1c-*`, `/merge1c`, `yolo`
и `/rewind` не являются контрактами нашего runtime.

## Хранилище конфигурации

Git и хранилище 1С — разные ресурсы. Разрешение на Git commit/push не означает
разрешение публикации в хранилище конфигурации. При этом ранее подтверждённое
разрешение на конкретное действие сохраняется: навык не требует повторного
согласования только из-за передачи контекста.

Перед изменением подтвердить привязку, точный repository/ИБ target, пользователя
и перечень объектов. Подобъект сопоставляется объекту-владельцу явно. Пустые и
неограниченные перечни не превращаются в операцию над всей конфигурацией.
Чужая блокировка требует изменения плана или решения владельца, а не force.
Частичный захват не равен атомарному успеху: сохранить результаты по объектам
и кто удерживает оставшиеся блокировки.

Проект задаёт фактический runner и параметры без раскрытия секретов. Семантические
группы операций для согласования с backend:

| Группа | Намерение | Существенные эффекты |
|---|---|---|
| status/history/diff | Получить факты о привязке, версиях и различиях | Может запускать платформу, читать credentials и писать отчёт |
| dump | Выгрузить определённую версию в новый файл | Читает repository, создаёт артефакт; не обновляет ИБ |
| lock/update | Захватить или получить выбранные объекты | Меняет shared locks или локальную конфигурацию; проверить свежесть источников |
| commit/unlock | Опубликовать выбранные изменения или освободить захват | Публикация/lock mutation; комментарий и фактический итог по объектам |
| force | Выполнить отдельно разрешённое исключение | Требует проектного allow и явного конкретного намерения; discard различать отдельно |

Bind/unbind, создание repository и управление пользователями — отдельная
административная задача, не обход обычного конфликта. Не менять проектную привязку
или allow-force, чтобы разблокировать собственный текущий шаг.

## Обновление поставщика / AI merge

Первый результат — план и классификация, не применение. Для сопоставления нужны
подтверждённые исходный поставщик, текущая конфигурация и новый поставщик с
идентификаторами артефактов. При отсутствующей базе сравнения классификация
остаётся неопределённой, не «автоматически безопасной».

Разделить изменения поставщика, свои изменения и конфликтующие изменения.
Расширение/CFE может быть выбранной стратегией для отдельных вмешательств;
это не универсальная гарантия совместимости, полноты обновления или переноса
данных. Заимствование объекта и патч метода требуют своих возможностей и проверки
применимости. Не объявлять donor `/merge1c`, MergeCfg, cfe-borrow или rewind
доступными, пока backend не подтверждает соответствующую операцию.

Применение идёт отдельным проектным runner по разрешённому плану и target,
с проверкой исходников, ограничений поддержки, platform build и свежего отчёта.
Блокировки и неизвестный итог сохраняются до подтверждённого завершения либо
восстановления. Никакого автоматического применения «потому что yolo».

## Бинарные артефакты

Обычная форма `Ext/Form.bin` и целый CF/CFE/EPF — различные маршруты. Расширение
файла и наличие инструмента недостаточны для выбора поддерживаемого codec.
Сначала проверить конкретную установленную возможность, версию, тип артефакта
и ограничения чтения/сборки. Source-only анализ не требует действующей ИБ.

Работать в новом workspace, сохранить исходный артефакт, manifest и непрозрачные
данные. Копирование/распаковка пишет файлы, даже когда не меняет ИБ. Сравнивать
логический payload и существенные свойства после пересборки; различающийся SHA
сам по себе не дефект, совпавший набор имён не доказывает сохранность структуры.
Пересборка утилитой не доказывает, что платформа загрузит бинарный результат.
Загрузку в ИБ и проверку исполнения рассматривать как отдельные эффекты.

Из donor полезны разделение codec и предупреждения по непрозрачным данным.
Версионные наблюдения о v8unpack 1.2.6 не следует переписывать как вечные свойства
всех версий. В canonical уже есть логические правила `getconfigfiles` и
`v8unpack-source-structure`; новый навык должен маршрутизировать к ним по
проектному индексу, а не заменять их ещё одной полной библиотекой.

## 1С:Элемент

Признаки `.xbsl`, парных YAML-файлов и `Проект.yaml` требуют отдельного пути
от классической платформы 8.x. В mixed-проекте ограничить вывод соответствующим
поддеревом; одного совпавшего имени недостаточно для переклассификации всего
репозитория.

DSH может читать/искать/править текст штатными средствами. Проверки XBSL,
сборка, запуск и публикация выполняются только реально доступным project tool
или средой Элемента. Отсутствие такого tool означает «не настроено», а не запрет
на будущую интеграцию. BSL LS, Designer, ibcmd и XML-dump 8.x не считаются
валидаторами XBSL. Новые SDK/линтеры/публикация не устанавливаются автоматически.

## Общее для четырёх маршрутов

- Backend различает available, unsupported и not-configured; кнопка в UI или
  Markdown-имя не выдаёт исполнителю capabilities.
- Оси task/role/access определяют подборку описаний, не авторизацию операции.
  Роли analyst/explorer подходят для исследования, metadata-manager/developer —
  для разрешённых изменений, reviewer/tester — для отдельных проверок по pipeline.
- Проектные runner bindings, эффекты, exact target и отчёт остаются явными.
  Нативные права, sandbox, reviewed-code trust и resource locks сохраняются.
- Возвращать фактическую область проверки, source/target/artifact identity,
  per-object/step результат и ограничения; неизвестный или частичный итог не
  превращать в PASS по одному exit code.

## Проверки после согласования API

1. Skill frontmatter, слой, условные references и замкнутость ресурсов.
2. Independent forward cases: repository partial lock/conflict; merge без
   исходного поставщика; ordinary form против целого CF; mixed XBSL/BSL проект.
3. Native fixtures: scope, права, эффекты, read-only отказ, отсутствие процесса
   при preview, source/target binding, unknown/partial результата и без обязательного
   фасада. Реальные хранилища/ИБ/деплой не запускать.
4. Canonical gates: `ci/check_layers.py`, `ci/check_composition.py`, unittest
   discovery, `ci/simulate_install.py --emit-inventory`.
5. Новый, не перезаписанный rulepack через `targets/dsh/rulepack/build.py`,
   затем `verify.py`; ожидаемый список станет 52 навыка после включения всех четырёх.
